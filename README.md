# Gift Sniper Bot для MRKT с классификацией монохромов по Gift Wiki

Telegram-бот, который:

* отслеживает новые листинги Telegram Gifts на маркете **MRKT**;
* применяет гибкие фильтры пользователя;
* классифицирует монохромы **только по данным Gift Wiki**;
* показывает три разных процента монохромов, не смешивая их;
* умеет покупать автоматически. Обычный режим и режим монохромов работают независимо.
  У покупок есть повторная проверка, лимиты, защита от двойной покупки и аварийная остановка.

> **По умолчанию бот ничего не покупает** (`RUN_MODE=dry_run`). Он показывает, что купил бы.
> Перед включением реальных покупок прочитайте раздел [«Статус интеграций»](#статус-интеграций).

## Статус интеграций

Подробности и ссылки на источники собраны в [`docs/DATA_SOURCES.md`](docs/DATA_SOURCES.md).

| Компонент | Статус |
|---|---|
| Telegram-бот (aiogram 3) | ✅ работает, покрыт сквозными тестами |
| PostgreSQL, миграции, Redis (блокировки, очереди, флаг аварийной остановки) | ✅ работает, проверено на реальных PostgreSQL 16 и Redis |
| **Gift Wiki** `GET /gifts/monochromes` | ✅ реализовано строго по документации `api.giftwiki.tg/docs`. Нужен `GIFTWIKI_API_KEY` (scope `collection:read`) |
| Gift Wiki: полный список моделей, вероятности выпадения, описания | ❌ в доступной документации нет. Бот показывает «Нет данных» |
| **MRKT** листинги, лента событий, карточка подарка, баланс | ⚠️ используется **неофициальный** API Mini App (`api.tgmrkt.io/api/v1`), описанный сообществом. Нужен токен вашего аккаунта |
| MRKT WebSocket | ❌ ни в одном источнике не описан. Используется опрос `POST /feed` с ограничением частоты |
| **MRKT покупка** `POST /gifts/buy` | ⚠️ описана сообществом. Проверить её можно только реальной покупкой. Официального разрешения на автоматизацию нет |

Среда разработки не имела сетевого доступа к `api.tgmrkt.io` и `api.giftwiki.tg` (политика прокси).
Поэтому ответы этих API в тестах воспроизведены по документации. На вашем сервере первым делом
выполните самопроверку:

```bash
docker compose run --rm bot python -m gift_sniper check
```

Команда проверяет авторизацию и формат ответов MRKT и Gift Wiki и печатает, что работает, а что нет.

## Быстрый старт (Docker Compose)

```bash
cp .env.example .env
# заполните: TELEGRAM_BOT_TOKEN, ADMIN_USER_IDS, POSTGRES_PASSWORD, GIFTWIKI_API_KEY,
#            TELEGRAM_API_ID, TELEGRAM_API_HASH
./scripts/setup.sh          # сборка, вход в Telegram для MRKT, запуск, самопроверка
docker compose logs -f bot
```

`scripts/setup.sh` нужен один раз; дальше достаточно `docker compose up -d`.

**Windows** (cmd или PowerShell, нужен запущенный Docker Desktop): вместо `setup.sh` выполните
`scripts\setup.cmd` из папки проекта. Если Проводник скрыл расширение и файл называется `.env.txt`,
переименуйте его: `ren .env.txt .env`.

Контейнер `bot` при старте применяет миграции (`python -m gift_sniper migrate`), затем запускает бота
и все фоновые задачи. Метрики и проверка состояния доступны на `http://127.0.0.1:9100/metrics`
и `/health`.

Если Docker Hub недоступен, образ можно собрать через зеркало:
`docker compose build --build-arg PYTHON_IMAGE=mirror.gcr.io/library/python:3.12-slim`.

### Без Docker

```bash
python3.12 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
export DATABASE_URL=postgresql+asyncpg://user:pass@localhost:5432/sniper REDIS_URL=redis://localhost:6379/0
PYTHONPATH=src python -m gift_sniper migrate
PYTHONPATH=src python -m gift_sniper run
```

Компоненты можно разнести по процессам:
`python -m gift_sniper run --components bot,scheduler` и `--components monitor,processor,buyer`.
Очереди и блокировки общие, через Redis.

### Команды

| Команда | Что делает |
|---|---|
| `python -m gift_sniper run [--components ...]` | запуск (`bot, monitor, processor, buyer, scheduler, metrics, webapp`) |
| `python -m gift_sniper migrate` | применить миграции Alembic |
| `python -m gift_sniper sync-giftwiki` | разовая синхронизация Gift Wiki |
| `python -m gift_sniper check` | самопроверка источников данных и интеграций |
| `python -m gift_sniper mrkt-login [--write-env .env] [--show] [--qr]` | один раз: вход в Telegram и получение токена MRKT (`--qr` — по QR-коду, без кода входа) |

## Настройка

Все секреты передаются только через переменные окружения (`.env`). В коде их нет. Полный список
с комментариями находится в [`.env.example`](.env.example). Главное:

| Переменная | Значение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен от @BotFather |
| `ADMIN_USER_IDS` | администраторы: аварийная остановка, режим работы, синхронизация Gift Wiki, `/map` |
| `ALLOWED_USER_IDS` | другие пользователи: уведомления, поиск, свои фильтры. Остальным доступ закрыт |
| `PURCHASE_USER_IDS` | кому разрешены покупки (по умолчанию только администраторам) |
| `RUN_MODE` | `notify_only` — только уведомления, `dry_run` — тестовый режим (по умолчанию), `live` — реальные покупки |
| `GIFTWIKI_API_KEY` | dev-ключ Gift Wiki со scope `collection:read` |
| `TELEGRAM_API_ID` / `TELEGRAM_API_HASH` | для `mrkt-login` и автообновления токена MRKT (см. ниже) |
| `MRKT_ACCESS_TOKEN` / `MRKT_INIT_DATA` | альтернативная авторизация MRKT |
| `MONOCHROME_ABSENT_PAIR_POLICY` | `not_monochrome` или `unknown`: как трактовать пару, которой нет в полном списке Gift Wiki |

### Авторизация MRKT

Рекомендуемый способ — ваша собственная Telegram-сессия (тот же поток, что в документации сообщества:
`RequestAppWebView(@mrkt, "app")` → `tgWebAppData` → `POST /auth`):

1. Получите `api_id` и `api_hash` на https://my.telegram.org → *API development tools* и впишите их
   в `.env` (`TELEGRAM_API_ID`, `TELEGRAM_API_HASH`).
2. Один раз выполните вход (интерактивно, в вашем терминале):

   ```bash
   docker compose run --rm -it bot python -m gift_sniper mrkt-login
   ```

   Telegram запросит номер телефона, код входа и пароль 2FA (если включён). Они вводятся только в
   этом терминале и уходят напрямую в Telegram; бот их не получает и не хранит (Pyrogram сохраняет
   лишь ключ авторизации сессии). Команда проверит, что MRKT выдаёт токен, и покажет баланс.

   Код входа приходит не по SMS, а в приложение Telegram — в чат «Telegram» на устройстве, где вы уже
   вошли. Если он не приходит, войдите по QR-коду: добавьте `--qr` (или `./scripts/setup.sh qr`,
   `scripts\setup.cmd qr`) и отсканируйте код в Telegram на телефоне: Настройки → Устройства →
   «Подключить устройство». Частые повторные запросы кода Telegram временно блокирует.
3. Запустите бота: `docker compose up -d`. Сессия лежит в томе `botdata` (`/app/data/mrkt.session`),
   и бот сам получает токен MRKT при старте и заново — если MRKT отклонит старый (не чаще раза в
   `MRKT_AUTH_COOLDOWN_SECONDS`).

> ⚠️ Файл сессии даёт полный доступ к вашему аккаунту Telegram. Не копируйте его и не публикуйте;
> завершить сессию можно в Telegram → Настройки → Устройства. После этого бот не сможет обновить
> токен MRKT, пока вы снова не выполните `mrkt-login`: команда сама удалит завершённую сессию и начнёт
> вход заново.

Альтернативы без сессии:

* `MRKT_ACCESS_TOKEN` — токен из ответа `https://api.tgmrkt.io/api/v1/auth` (DevTools → Network в
  веб-версии Telegram) или из `mrkt-login --write-env .env --show`. Без сессии бот не сможет обновить
  его сам: при HTTP 401 мониторинг приостановится, администраторы получат уведомление.
* `MRKT_INIT_DATA` — строка `tgWebAppData` Mini App; бот обменяет её на токен через `POST /auth`.

Все покупки выполняются с одного аккаунта MRKT. Бюджеты пользователей — это внутренние лимиты бота
поверх этого аккаунта.

### Рекомендуемый порядок включения

1. `RUN_MODE=dry_run`, `mrkt-login`, затем `python -m gift_sniper check`.
2. В боте: 💰 **Бюджет и лимиты** → задайте общие лимиты (на покупку, на день, всего). Без них покупки
   блокируются даже в тестовом режиме, чтобы тест честно отражал боевое поведение.
3. Создайте фильтры, включите режимы и посмотрите уведомления «🧪 был бы куплен».
4. Сделайте одну ручную покупку недорогого подарка (кнопка «🛒 Купить» в уведомлении) в `RUN_MODE=live`
   и проверьте результат в 📜 **История операций** и в самом MRKT.
5. Только после этого включайте автопокупку по фильтрам.

## Мини-приложение

Самый простой способ настроить покупки — мини-приложение Telegram: кнопка **«Снайпер»** слева от поля
ввода в чате с ботом, первая кнопка главного меню «📱 Открыть мини-приложение» или команда `/app`.

Внизу — четыре раздела: **Коллекции**, **Берёт бот**, **Лимиты**, **История**. Внутри коллекции работает
кнопка «Назад» Telegram, а сохранение — большая кнопка Telegram внизу экрана («Сохранить · 3 позиции»):
она появляется, только когда есть несохранённые изменения, а при уходе со страницы приложение спросит,
сохранить ли их. Оформление следует теме Telegram (тёмной или светлой).

* **Коллекции**: сетка карточек с обложкой с Fragment, флором и долей монохромных моделей («моно 50%»);
  поиск, фильтры «Все / Бот берёт / С монохромами» и сортировка. На карточке видно, сколько бот берёт
  в коллекции и покупает он сам (🛒) или только уведомляет (🔔).
* **Коллекция**: переключатель «🛒 Покупать / 🔔 Уведомлять» для всего, что выбрано в коллекции; строка
  «Вся коллекция» (любой подарок или любой монохром до своей цены); сетка моделей — картинка на цвете
  монохромного фона, флор, редкость и «моно %» — шанс монохрома (сумма редкостей монохромных фонов модели
  по данным MRKT, то есть доля копий модели с монохромным фоном).
* **Модель**: «Любой фон» и «Все монохромы» до своей цены, ниже — монохромные фоны по Gift Wiki: модель
  на цветном фоне, уровень монохрома (`high` / `medium` / `low` / `combo`; процента Gift Wiki не публикует),
  редкость фона и цена. Фон выбирается нажатием на карточку; новая галочка берёт цену из поля «Цена для
  отмеченных», общей цены монохромов или флора модели — её видно и можно изменить. «Выбрать все» и
  «Применить» задают одну цену сразу нескольким фонам. Цена отдельного фона важнее цены «Все монохромы».
* **Берёт бот**: всё выбранное по коллекциям одной карточкой — список «модель · фон · до цены», выключатель,
  «Изменить», «Покупать / Уведомлять», «Удалить»; отдельно — фильтры, созданные в чате.
* **Лимиты**: режим работы, что осталось сделать до покупок, общие лимиты, автопокупка обычных подарков
  и монохромов, пауза и аварийная остановка.
* **История**: покупки по дням с картинкой подарка и статусом; нажатие открывает подарок в Telegram.

Выбор в коллекции хранится как два фильтра («📱 Коллекция» и «📱 Коллекция · монохромы») со списком пар и
цен, поэтому покупка проходит все те же проверки: цена и наличие перед покупкой, бюджеты, режим работы,
а монохромные пары — ещё и статус MONOCHROME по свежим данным Gift Wiki. В меню фильтров чата они не
показываются (там только их число). Если бот ещё не может покупать, сверху появляется жёлтая плашка,
а точка на разделе «Лимиты» ведёт к списку недостающих шагов.

**Картинки.** Обложка коллекции — `https://fragment.com/file/gifts/<имя>/thumb.webp`, конкретный подарок —
`https://nft.fragment.com/gift/<имя>-<номер>.webp` (форматы из справочника сообщества
[Nxrix/Telegram-Gifts](https://github.com/Nxrix/Telegram-Gifts)). Пара «модель + фон» — `photo_url` записи
Gift Wiki, а если его нет — подарок с этой парой, который бот видел на MRKT. Картинки загружает телефон
напрямую с этих сайтов.

**Как оно доступно из Telegram.** Telegram открывает мини-приложения только по HTTPS. В Docker Compose это
делает сервис `tunnel` — бесплатный туннель Cloudflare без регистрации: бот сам узнаёт его адрес
(`*.trycloudflare.com`) и ставит кнопку меню; после перезапуска адрес меняется, и бот обновляет кнопку.
Страница открыта по ссылке, но её API отвечает только на запросы с подписью Telegram от пользователей
из `ADMIN_USER_IDS` / `ALLOWED_USER_IDS`. Свой домен: задайте `WEBAPP_URL=https://ваш-домен/app/`,
направьте его на порт `WEBAPP_PORT` (8080) контейнера `bot`, а сервис `tunnel` можно не запускать.

Модели коллекции бот берёт из `POST /gifts/models` MRKT (запрос описан в tgmrkts, поля ответа — нет;
`check` показывает, распознались ли они), иначе — модели, замеченные в листингах.

## Использование бота

`/start` открывает главное меню:

* 🎁 **Автопокупка подарков**: включение режима, его бюджет, фильтры режима.
* ⚫ **Автопокупка монохромов**: независимый режим со своим бюджетом. Покупает **только** `MONOCHROME`.
* 🔎 **Поиск по фильтрам**: текущие листинги MRKT по выбранному фильтру и доля монохромов в выборке.
* 🆕 **Новые листинги**: последние обнаруженные объявления, карточка «Подробнее».
* 📚 **Gift Wiki**: состояние синхронизации, подарки с монохромными записями, сопоставление коллекций.
* 📊 **Статистика рынка** и 📈 **Моя статистика**: показатели за период с указанием источника.
* ⚙️ **Настройки фильтров**: создание, редактирование всех полей, копирование, включение и
  выключение, удаление; 🔔 настройки уведомлений.
* 💰 **Бюджет и лимиты**: общие лимиты и лимиты каждого режима.
* 📜 **История операций**: все попытки покупки со статусами и причинами.
* ⏸ **Управление ботом**: ⛔ остановка всех покупок, пауза своих автопокупок, режим работы.

Команды: `/app` — мини-приложение, `/stop` — немедленная остановка всех автоматических покупок, `/cancel` — отмена ввода,
`/map` — ручное сопоставление коллекций (для администраторов).

### Фильтры

Доступные условия: цена от и до, коллекции, модели, фоны, символы, исключённые коллекции и модели,
редкость модели, фона и символа (в ‰ по данным MRKT), «только новые листинги», минимальная скидка.
Для монохромов дополнительно: типы Gift Wiki (`high/medium/low/combo`) и минимальная доля
монохромных моделей коллекции.

Лимиты фильтра: сколько купить, максимальная цена подарка, максимальная сумма операции, бюджет на
день и всего, максимум покупок за период. Каждый фильтр включается отдельно и отдельно разрешает
автопокупку. У каждого фильтра есть своя статистика срабатываний и история покупок.

Скидка считается прозрачно: (медиана наблюдённых цен той же коллекции и модели за `DISCOUNT_WINDOW_DAYS`
дней − цена) / медиана × 100%. Нужно не меньше `DISCOUNT_MIN_SAMPLES` наблюдений. Если данных
недостаточно, условие не выполняется. Бот никогда не называет подарок выгодным только из-за редкости.

## Монохромы

### Классификация

Gift Wiki классифицирует **пары «модель + фон»** внутри подарка и присваивает каждой уровень
`high / medium / low / combo`. Поэтому:

| Статус | Когда |
|---|---|
| `MONOCHROME` | в Gift Wiki есть запись с тем же подарком (коллекцией), моделью и фоном. Если цвета фона есть и в MRKT, и в Gift Wiki, они совпадают |
| `NOT_MONOCHROME` | полный список монохромов подарка получен (поиск `gift_name` или полная пагинация), в нём есть записи, но этой пары нет. Данные не старше `GIFTWIKI_STALE_AFTER_HOURS` |
| `UNKNOWN` | всё остальное: коллекции нет в Gift Wiki, сопоставление неоднозначно, нет модели или фона, список неполный или устарел, у подарка нет записей, недокументированный тип, расхождение цветов |

Название модели («Black», «Onyx» и т. п.) никогда не делает подарок монохромом. При неоднозначном
сопоставлении бот ничего не выбирает сам: администратор задаёт соответствие командой `/map`.
Соответствия хранятся в таблице `collection_mappings`. Классификация активных листингов
пересчитывается после каждой синхронизации.

### Три процента

| Показатель | Формула | Источник |
|---|---|---|
| **A. Доля монохромных моделей** | моделей, у которых есть хотя бы одна монохромная запись / известных моделей коллекции × 100% | Gift Wiki (+ список моделей, замеченных на MRKT) |
| **B. Вероятность выпадения модели** | показывается, только если её публикует Gift Wiki. В документированном API её нет, поэтому «Нет данных» | Gift Wiki |
| **C. Доля монохромных листингов** | подтверждённых `MONOCHROME` / всех подходящих объявлений × 100%, например «12 из 80 объявлений — 15%» | MRKT |

Правила расчёта:

* отсутствующие данные не заменяются нулём;
* `UNKNOWN` входит в знаменатель C, но никогда в числитель. Количество неизвестных показывается отдельно;
* A всегда помечается «по известным моделям». Если моделей коллекции на MRKT ещё не видели, A равно
  «Нет данных», а не фиктивным 100%;
* вероятности атрибутов не перемножаются;
* доля моделей не выдаётся за вероятность получить монохром;
* редкость (‰ MRKT) показывается отдельно от вероятности Gift Wiki.

## Покупки

### Алгоритм

1. Монитор обнаруживает листинг. Событие дедуплицируется в Redis и по первичному ключу в PostgreSQL.
2. Обработчик классифицирует листинг, проверяет все фильтры и **сначала** ставит задачу покупки,
   затем отправляет уведомления.
3. `PurchaseService`:
   * проверяет режим работы, аварийную остановку, права пользователя и переключатели режимов;
   * берёт **Redis-блокировку** на id подарка, общую для всех процессов;
   * проверяет в БД, что по подарку нет активной попытки;
   * **заново запрашивает объявление** на MRKT: проверяет наличие, текущую цену и атрибуты;
   * повторно проверяет фильтр, а для монохромов ещё и статус `MONOCHROME` и свежесть данных Gift Wiki;
   * резервирует бюджет одной транзакцией под блокировкой строки пользователя (`SELECT … FOR UPDATE`):
     общий лимит, лимит режима и лимиты фильтра;
   * в `dry_run` записывает «был бы куплен» и не отправляет запрос;
   * в `live` проверяет баланс MRKT и ещё раз аварийную остановку. Если снимок старше
     `PURCHASE_MAX_SNAPSHOT_AGE_SECONDS`, перепроверяет цену. Затем фиксирует статус `submitted`
     и отправляет **один** запрос `POST /gifts/buy`.
4. Результат сохраняется, а пользователь получает уведомление. Сообщение «✅ Покупка подтверждена»
   отправляется **только** после подтверждения MRKT: ответа с данными покупки или проверки владения
   подарком.

### Защита от двойных покупок

* Redis-блокировка на подарок защищает от параллельных задач, фильтров и пользователей.
* Частичный уникальный индекс `uq_purchase_attempts_live_gift` не даёт создать вторую живую попытку
  на тот же подарок, даже если блокировка потеряна.
* Повторная доставка сообщения из очереди безопасна: обработчики идемпотентны.
* Тесты: 5 одновременных запросов на один подарок (разные фильтры и пользователи) дают ровно
  один запрос покупки.

### Неопределённый результат

Запрос покупки **никогда не повторяется автоматически** после сетевой ошибки. Результат
классифицируется так:

* `confirmed`: 2xx с данными покупки;
* `rejected` (точно не выполнена): 4xx, или соединение не было установлено (запрос не отправлялся);
* `uncertain`: таймаут после отправки, разрыв соединения, 5xx, 2xx без данных.

При `uncertain` бот проверяет подарок: `isMine` → подтверждено; продолжает продаваться (два
согласованных наблюдения) → «не выполнено»; снят и не наш → куплен другим покупателем. Повтор
разрешён только после **проверенного** невыполнения, с полной перепроверкой и не чаще
`PURCHASE_RETRIES_AFTER_VERIFIED_FAILURE` раз. Если проверка ничего не дала, статус остаётся
`unknown`, бюджет остаётся зарезервированным, повторная покупка запрещена, а фоновая задача проверяет
попытку каждые 60 секунд. Если состояние не прояснилось за 24 часа, бот уведомляет администраторов.
После перезапуска `reserved` переводится в `cancelled` (запрос точно не отправлялся), а `submitted` —
в `unknown`, после чего попытка проверяется.

### Бюджеты

* Общие лимиты пользователя: на покупку, на день и всего. Без них покупки блокируются.
* Независимые бюджеты режимов «подарки» и «монохромы»: на покупку, на день, всего, покупок за период.
  Общий лимит соблюдается всегда.
* Лимиты фильтра.
* Расходом считаются подтверждённые покупки и операции с неизвестным результатом. Тестовый режим
  учитывается отдельно.
* Дневной лимит считается по календарному дню в часовом поясе `TIMEZONE`.

### Аварийная остановка

`/stop` или кнопка ⛔ мгновенно запрещают новые покупки. Флаг проверяется перед каждой покупкой и
непосредственно перед отправкой запроса. Он хранится в Redis и дублируется в PostgreSQL, поэтому
переживает перезапуск. Если Redis недоступен, покупки считаются остановленными. Уже отправленный
запрос отозвать невозможно.

## Уведомления

Настраиваются: все новые листинги, только подходящие, отдельно монохромы, снижение цены (с порогом
в %), успешные покупки, ошибки, диапазон цен, коллекции, порог доли монохромных моделей, частота
(не больше N в минуту) и режим без повторных сообщений. Повторные сообщения об одном объявлении
блокируются уникальным ключом в БД. Лимит частоты считается в Redis. Сообщения о покупках и
ошибках доставляются всегда. Общий поток в Telegram ограничен, ответы `RetryAfter` обрабатываются.

## Наблюдаемость

* `GET /metrics` (Prometheus) отдаёт:
  * задержку обнаружения листинга (`sniper_listing_detection_latency_seconds`);
  * время обработки фильтров (`sniper_filter_processing_seconds`);
  * время от обнаружения до решения о покупке;
  * запросы к внешним API по статусам;
  * попытки покупки по статусам;
  * уведомления;
  * возраст данных Gift Wiki;
  * очереди;
  * флаг аварийной остановки.
* `GET /health` показывает состояние PostgreSQL и Redis, время последнего опроса MRKT, возраст
  данных Gift Wiki и режим работы.
* Логи пишутся в JSON (`LOG_FORMAT=json`), токены маскируются.
* В PostgreSQL ведутся `audit_log` (журнал операций), `error_logs`, история синхронизаций Gift Wiki
  и история цен.

## Ограничения и риски

* У MRKT нет официального публичного API. Используемые эндпоинты могут измениться, а условия MRKT
  об автоматизации не опубликованы. Ответственность за включение `live` лежит на операторе.
* У `POST /gifts/buy` нет параметра «максимальная цена». Если продавец поднимет цену в миллисекунды
  между перепроверкой и покупкой, MRKT может списать новую цену. Бот сокращает это окно и учитывает
  фактическую цену из ответа в бюджете.
* Gift Wiki публикует только монохромные записи. Полный список моделей и вероятности в доступном API
  отсутствуют, поэтому доля A считается по известным моделям, а B равна «Нет данных».
* Ссылка на конкретный подарок в MRKT не задокументирована. Поэтому кнопка «Открыть в MRKT» появляется,
  только если задан `MRKT_LISTING_URL_TEMPLATE` (шаблон берётся из ссылки «Поделиться» подарка в MRKT).
  Кнопка «🎁 В Telegram» (`t.me/nft/<slug>`) строится, только если MRKT отдаёт slug.
