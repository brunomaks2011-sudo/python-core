# Тестування

## Автоматичні тести

Тести написані на вбудованому в Node.js раннері (`node:test`) і запускаються через `tsx`.

| Набір | Що перевіряє | Потрібна БД |
|---|---|---|
| `tests/unit/*` | розбір української мови (ціни «до двох тисяч», вік, номери наборів, кількість словами), розпізнавання намірів на прикладах із ТЗ, валідація телефону/імені/міста/цін, перевірка вигаданих чисел у відповідях ШІ, переходи статусів, налаштування `.env` | ні |
| `tests/integration/orders.test.ts` | резерв і склад на реальній PostgreSQL: приклад «5 → 4 → +3 → 7», подвійне підтвердження, **одночасні замовлення на останній набір**, 10 покупців на 3 набори, ціна змінилася після підсумку, скасування повертає резерв, відправлення списує один раз, повернення лише після підтвердження власником, CHECK-обмеження, черга сповіщень і повторні спроби, `/forgetme` | так |
| `tests/integration/bot.e2e.test.ts` | повний діалог через фейковий сервер Telegram Bot API: пошук, перевірка наявності, оформлення з кнопками, зміна даних, питання посеред оформлення, права адміністратора, `/addstock`, статуси з ТТН, майстер `/addproduct` із фото, розсилка з підтвердженням, дедуплікація `update_id` | так |
| `tests/integration/assistant.test.ts` | інтеграція з Claude API на записаних відповідях (без реальних запитів): цикл інструментів, параметри запиту (модель, `effort`, `fallbacks`, strict-схеми, кешування), заміна вигаданої ціни, `refusal`, помилка API → резервний розбір, ШІ лише починає оформлення | так |

### Запуск

1. Створіть **окрему** тестову базу (тести очищають усі її таблиці; назва має містити `test`):
   ```bash
   sudo -u postgres psql -c "CREATE DATABASE lego_shop_test OWNER lego;"
   ```
2. Вкажіть її адресу (якщо відрізняється від стандартної
   `postgresql://lego:lego_dev_password@localhost:5432/lego_shop_test?schema=public`):
   ```bash
   export TEST_DATABASE_URL="postgresql://lego:пароль@localhost:5432/lego_shop_test?schema=public"
   ```
3. Запуск:
   ```bash
   npm run typecheck          # перевірка типів
   npm run test:unit          # лише unit-тести (без БД)
   npm test                   # усі тести; міграції тестової БД застосовуються автоматично
   ```
   Детальні логи під час тестів: `TEST_LOG_LEVEL=debug npm test`.

### Ручні перевірки без Telegram

```bash
npx tsx tests/manual/transcript.ts   # друкує повний діалог покупця й власника (фейковий Telegram, тестова БД)
npm run build && npx tsx tests/manual/smoke.ts   # запускає dist/index.js: старт, /start, health-check, SIGTERM
```

## Ручне тестування в Telegram

Підготовка: заповніть каталог демонстраційними даними (`npm run db:seed`) і візьміть два
акаунти Telegram — **власника** (його ID в `ADMIN_IDS`) і **покупця**. Залишки зручно
перевіряти командою `/stock` (колонки «на складі / у резерві / доступно»).

### Сценарій 1. Замовлення зменшує доступний залишок (5 → 4)

| Крок | Дія | Очікуваний результат |
|---|---|---|
| 1 | Власник: `/stock` | `42151` — **5/0/5** |
| 2 | Покупець: «Привіт! Є LEGO Technic?» | Список наборів LEGO Technic із цінами з каталогу та позначкою «Ціни та наявність перевірено…» |
| 3 | Покупець: «Чи є LEGO 42151?» | Картка: «Так, LEGO Technic 42151 «Bugatti Bolide» є в наявності!», ціна 1 800 грн, «В наявності: 5 шт.», кнопка «🛒 Замовити» |
| 4 | «🛒 Замовити» → кількість **1** → ім’я → телефон (кнопка «📱 Надіслати мій номер») → місто → відділення → оплата | Кожен крок запитується один раз; некоректний телефон/ім’я — пояснення помилки |
| 5 | Підсумок | Набір, номер 42151, кількість, ціна за одиницю, загальна вартість, доставка, оплата + кнопки «Підтвердити / Змінити дані / Скасувати» |
| 6 | «✅ Підтвердити замовлення» | Покупець: «Дякуємо за замовлення! 🎉 Номер замовлення: №101… Статус: очікує підтвердження магазину». Власник: «🆕 Нове замовлення №101» з кнопками |
| 7 | Власник: `/stock` | `42151` — **5/1/4** (доступно зменшилося з 5 до 4) |
| 8 | Покупець ще раз натискає «Підтвердити» на старому підсумку | «Це замовлення вже оформлено: №101» — друге замовлення не створюється |

### Сценарій 2. Надходження товару (4 → 7)

| Крок | Дія | Очікуваний результат |
|---|---|---|
| 1 | Власник: `/addstock 42151 3 нова поставка` | «Додано 3 шт. На складі: 8, у резерві: 1, доступно покупцям: 7» |
| 2 | Власник: `/editproduct 42151` → «📜 Історія змін» | Записи: резерв (№101), надходження +3 з коментарем |

### Сценарій 3. Статуси без повторного списання

| Крок | Дія | Очікуваний результат |
|---|---|---|
| 1 | Власник у сповіщенні: «✅ Підтвердити» | Покупцю: «Ваше замовлення №101 підтверджено магазином!» |
| 2 | `/order 101` → «🚚 Відправлене» → ввести ТТН `20450012345678` | Покупцю: «Замовлення №101 відправлено!» + ТТН; `/stock`: **7/0/7** (товар списано зі складу, резерв знято) |
| 3 | «🎉 Доставлене» | Покупцю: «Замовлення №101 доставлено…»; `/stock` без змін — **7/0/7**; у `/customers` сума покупок покупця зросла на 1 800 грн |
| 4 | Спроба скасувати доставлене замовлення | «Неможливо…» — відправлене замовлення можна лише оформити як повернення |

### Сценарій 4. Скасування повертає резерв

| Крок | Дія | Очікуваний результат |
|---|---|---|
| 1 | Покупець оформлює ще 2 шт. `42151` | `/stock`: **7/2/5** |
| 2 | Власник: `/order 102` → «❌ Скасувати» → підтвердження | Покупцю: «Замовлення №102 скасовано»; `/stock`: **7/0/7** |

### Сценарій 5. Повернення

| Крок | Дія | Очікуваний результат |
|---|---|---|
| 1 | Для доставленого №101: «↩️ Повернення» → підтвердити | Статус «повернення»; склад поки **не змінюється** |
| 2 | Коли товар фізично повернувся: «📦 Товар повернувся на склад» | `/stock`: на складі +1. Повторне натискання — «Повернення вже оброблено» |
| 2а | Альтернатива: «🗑 Не повертати на склад (брак)» | Склад не змінюється, повернення закрито |

### Сценарій 6. Останній набір і нестача товару

| Крок | Дія | Очікуваний результат |
|---|---|---|
| 1 | Знайдіть товар із залишком 1 (у демо — `75257`) | — |
| 2 | Два покупці одночасно доходять до підсумку й обидва тиснуть «Підтвердити» | Одне замовлення створено; другий покупець отримує «цей набір щойно закінчився» + схожі набори в наявності |
| 3 | Покупець вводить кількість більшу за залишок | «Зараз доступно лише N шт.» — замовлення на недоступну кількість не оформлюється |
| 4 | Власник: `/editproduct 75257` → «➖ Списати» `5` | Відмова: можна списати лише вільний (не зарезервований під замовлення) товар — бот покаже, скільки саме |

### Сценарій 7. Розуміння мови (з Claude API та без нього)

Повідомлення: «Є технік?», «Покажи зоряні війни», «Що є до двох тисяч?», «Які набори є для дітей
від 8 років?», «Скільки коштує цей лего?» (після показу картки), «Хочу замовити два набори»,
«Я вже у вас купував», «Чи є LEGO 10497?» (немає в наявності), «Шукаю 99999» (немає в каталозі).

Очікування: показуються лише товари з бази; ціни й залишки збігаються з `/stock`; для відсутніх
товарів — чесна відповідь і реальні альтернативи; при «хочу замовити» бот починає оформлення, але
замовлення створюється лише після підтвердження кнопкою. Повторіть із `AI_ENABLED=false` —
бот має відповідати так само по суті (резервний розбір).

### Сценарій 8. Права та персональні дані

- Покупець надсилає `/admin`, `/stock` → «Ця команда доступна лише власнику магазину».
- `/broadcast` у власника: текст → попередній перегляд → без натискання «Так, надіслати» нічого не надсилається; покупець після `/unsubscribe` розсилку не отримує.
- `/forgetme` при активному замовленні → відмова з номерами замовлень; після завершення — дані знеособлено, `/customers` показує «Дані видалено на вимогу покупця».

### Сценарій 9. Відновлення після перезапуску

1. Покупець зупиняється посеред оформлення (наприклад, після введення міста).
2. Перезапустіть бота (`docker compose restart bot` / `systemctl restart shop-lego-bot`).
3. Покупець вводить відділення — оформлення продовжується з того ж місця; кнопка «▶️ Продовжити оформлення» також працює.
