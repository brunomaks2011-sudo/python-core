# Источники данных: что проверено и какие есть ограничения

Документ фиксирует результаты проверки источников до начала реализации (п. 15 ТЗ).
Всё, что бот делает с внешними системами, опирается только на описанное здесь.
Если поле или эндпоинт здесь не описан, бот его не использует.

Дата проверки: 2026-10-23.

## Проверка доступности из среды разработки

Сетевая политика облачной среды разработки блокировала `api.giftwiki.tg`, `api.tgmrkt.io` и `t.me`
(ответ прокси 403 на CONNECT). Поэтому ни один запрос к живым API из среды разработки не выполнялся.
Код интеграций написан по документации (см. ниже) и покрыт тестами на записанных по документации
ответах. Перед боевым запуском выполните самопроверку на сервере с доступом в интернет:

```bash
docker compose run --rm bot python -m gift_sniper check
```

Команда проверяет авторизацию и формат ответов MRKT и Gift Wiki и печатает, какие компоненты работают.

## 1. Gift Wiki (`api.giftwiki.tg`)

Источник спецификации: Swagger UI `https://api.giftwiki.tg/docs`, раздел **Gift Monochromes**,
операция `GET /gifts/monochromes` («List gift monochrome metadata»). Спецификация получена от заказчика
в виде снимков экрана документации.

### Авторизация

* Заголовок `X-API-Key: <ключ>`: dev API key со scope `collection:read`.
  Также принимается `Authorization: ApiKey <ключ>`.
* `401 Unauthorized`: тело `{"error": "..."}`.
* `403 Forbidden`: «Bearer app users cannot use gift_id/gift_name lookup filters», тело `{"error": "..."}`.

### Параметры запроса

| Параметр | Где | Описание из документации |
|---|---|---|
| `page` | query, integer, по умолчанию 1 | Номер страницы списка из 21 записи. Игнорируется при `gift_id`/`gift_name`. |
| `limit` | query, integer, по умолчанию 21 | Принимается для совместимости, публичный список фиксирован на 21 записи. |
| `gift_id` | query, string | Поиск по id подарка. Только API key/admin. Возвращает все подходящие записи. |
| `collection_id` | query, string | ObjectId публичной коллекции: только записи, чья пара gift/model есть в коллекции. |
| `gift_name` | query, string | Поиск по названию подарка. Только API key/admin. Возвращает все подходящие записи. |
| `model_name` | query, string | Фильтр по модели. |
| `backdrop_name` | query, string | Фильтр по фону. |
| `type` | query, string | Одна или несколько классификаций: `low`, `medium`, `high`, `combo`. Одно значение, повтор параметра или список через запятую. |

Сортировка: по `type` в порядке `high, medium, low, combo`, затем от новых к старым.

### Ответ 200

Массив записей. Поля из примера в документации:

```json
[
  {
    "_id": "string",
    "gift_id": "string",
    "gift_name": "string",
    "model_name": "string",
    "backdrop_name": "string",
    "type": "low",
    "center_color": "string",
    "edge_color": "string",
    "pattern_color": "string",
    "text_color": "string",
    "photo_url": "string",
    "animation_url": "string"
  }
]
```

На снимке пример обрезан после `animation_url`. Остальные поля не известны, поэтому бот их не
интерпретирует. Запись целиком сохраняется в `giftwiki_monochromes.raw` (JSONB), чтобы новые поля
можно было подключить позже без повторной загрузки.

### Выводы для реализации

1. **Монохром в Gift Wiki — это классификация пары «модель + фон» внутри подарка, а не модели целиком.**
   Каждая запись описывает пару (`gift_name`, `model_name`, `backdrop_name`) и её уровень `type`.
   Поэтому:
   * листинг MRKT получает статус `MONOCHROME`, только если в Gift Wiki есть запись с тем же подарком,
     той же моделью и тем же фоном;
   * «монохромной моделью» в формуле доли (п. 5A ТЗ) считается модель, у которой в Gift Wiki есть
     хотя бы одна монохромная запись (с любым фоном).
2. Уровни `high / medium / low / combo` показываются как есть, без собственных толкований.
   Значение `combo` в документации не раскрыто, и бот его не интерпретирует.
   В фильтрах монохромов можно ограничить допустимые уровни.
   Запись с недокументированным значением `type` даёт статус `UNKNOWN`.
3. Поиск по `gift_name` возвращает **все** записи подарка. Бот использует его, чтобы получить полный
   список монохромных пар подарка. Если полный список подарка получен и содержит хотя бы одну запись,
   а пары листинга в нём нет, листинг получает `NOT_MONOCHROME` (настройка
   `MONOCHROME_ABSENT_PAIR_POLICY`, можно переключить на `unknown`). Если у подарка нет ни одной записи,
   нельзя отличить «нет монохромов» от «ещё не каталогизирован», поэтому статус `UNKNOWN`.
4. Поля `center_color / edge_color / pattern_color / text_color` совпадают по смыслу с цветами фона
   Telegram. MRKT отдаёт цвета фона листинга (`backdropColorsCenterColor`, `backdropColorsEdgeColor`).
   Если цвета есть с обеих сторон и формат удаётся разобрать, бот сверяет их. Расхождение даёт `UNKNOWN`.
5. **Не опубликовано в доступной документации**, поэтому в боте показывается «Нет данных»:
   * полный список моделей подарка, фоны и символы вне монохромных записей;
   * описания моделей;
   * вероятности выпадения моделей;
   * ссылки на веб-страницы Gift Wiki (формат URL страниц не задокументирован).
     Бот показывает `photo_url` записи и ссылку на публичный канал Gift Wiki (`GIFTWIKI_PUBLIC_URL`).
6. Знаменатель доли монохромных моделей (п. 5A) — «известные модели подарка». Это объединение
   моделей из записей Gift Wiki и моделей, которые бот видел в листингах MRKT. Бот всегда помечает,
   что расчёт сделан по известным моделям. Если моделей коллекции на MRKT ещё не видели, доля равна
   «Нет данных»: иначе знаменатель состоял бы из одних монохромных моделей и давал бы фиктивные 100%.
   Чтобы оценить полноту списка, бот также показывает сумму редкостей известных моделей по данным
   MRKT (около 1000‰ означает полный набор).

Если в документации Gift Wiki есть эндпоинты моделей, фонов, символов или вероятностей, пришлите их
описание. Клиент `gift_sniper/integrations/giftwiki/client.py` расширяется новым методом, а таблицы
уже готовы хранить эти данные с источником и временем получения.

## 2. MRKT (`api.tgmrkt.io`)

### Статус интерфейса

**Официального публичного API, документации или условий использования для разработчиков найти не удалось.**
MRKT работает как Telegram Mini App (`@mrkt`, short name `app`). Его фронтенд (`cdn.tgmrkt.io`) обращается
к `https://api.tgmrkt.io/api/v1`. Этот интерфейс описан только неофициально, сообществом:

* [boostNT/MRKT-API](https://github.com/boostNT/MRKT-API): неофициальная документация (ru);
* [aiofake/tgmrkt](https://github.com/aiofake/tgmrkt) (PyPI `tgmrkts`): асинхронный клиент;
* PyPI `amrkt` 1.6.0: асинхронный клиент с pydantic-моделями ответов.

Все три источника согласованно описывают перечисленные ниже эндпоинты. Бот использует только их.

> ⚠️ Внутренний API Mini App может измениться без предупреждения, а явного разрешения MRKT на
> автоматизацию нет. Поэтому по умолчанию бот работает в режиме `RUN_MODE=dry_run` и ничего не покупает.
> Включайте `live`, только если вы убедились, что MRKT допускает автоматические покупки с вашего аккаунта.

### Авторизация

* `POST /auth` с телом `{"data": "<initData Telegram WebApp>"}` возвращает `{"token": "..."}`.
  `initData` выдаёт Telegram при открытии Mini App вашим аккаунтом.
* Альтернатива из документации: скопировать токен из ответа `/auth` во вкладке Network веб-версии Telegram.
* Заголовок: `Authorization: <token>` (boostNT, amrkt) или `Authorization: Bearer <token>` (tgmrkts).
  Формат задаётся настройкой `MRKT_AUTH_HEADER_FORMAT` (`raw` по умолчанию).
* Документация требует `Referer: https://cdn.tgmrkt.io/`.
* Срок жизни токена неизвестен (по документации «точно более суток»).

Рекомендуемый способ получения токена — команда `python -m gift_sniper mrkt-login`: она выполняет
именно этот поток документации (Kurigram/Pyrogram: `RequestAppWebView` к `@mrkt` с short name `app`,
затем `POST /auth`). Вход в Telegram (телефон, код, пароль 2FA) происходит только в терминале оператора;
бот никогда не спрашивает их в чате. Сохранённая сессия позволяет боту самому обновлять токен при
HTTP 401 (не чаще раза в `MRKT_AUTH_COOLDOWN_SECONDS`). Сессия даёт полный доступ к аккаунту Telegram.
Бот не подделывает браузерные TLS-отпечатки и не ротирует User-Agent, хотя часть клиентов сообщества так делает.

### Используемые эндпоинты

| Назначение | Запрос | Источник |
|---|---|---|
| Листинги с фильтрами | `POST /gifts/saling` (`collectionNames`, `modelNames`, `backdropNames`, `symbolNames`, `minPrice`, `maxPrice`, `ordering`, `lowToHigh`, `count`≤20, `cursor`) → `{"gifts": [...], "cursor": ...}` | boostNT, tgmrkts, amrkt |
| Лента событий рынка | `POST /feed` (`type`: `listing`, `sale`, `return`, `unlisting`, `change_price`, `upload`; `ordering: "Latest"`, `count`, `cursor`) → `{"items": [{"type","id","gift","amount","date"}]}`. Проверено 2026-10-24: фильтр `type` со значением `change_price` MRKT отклоняет (HTTP 400, `Error converting value "change_price" to type 'FeedItemType'`), поэтому бот отправляет `type: []` и отбирает типы событий сам | tgmrkts, amrkt |
| Карточка подарка (повторная проверка) | `GET /gifts/gift/{id}` | amrkt |
| Покупка | `POST /gifts/buy` `{"ids": [id]}` → `[{"userGift": {...}, "price": int}]` | tgmrkts, amrkt |
| Баланс | `GET /balance` → `{"hard": nanoTON, ...}` | tgmrkts, amrkt |
| Коллекции | `GET /gifts/collections` → `[{"name","title","floorPriceNanoTons",...}]` | tgmrkts, amrkt |
| Инвентарь (проверка результата) | `POST /gifts` с фильтрами и `number` | tgmrkts, amrkt |
| Модели и фоны коллекции (мини-приложение) | `POST /gifts/models`, `POST /gifts/backdrops` `{"collections": [name]}`. Поля ответа в источнике не описаны: бот читает `modelName`/`backdropName`/`name`, `...RarityPerMille`/`rarityPerMille`, `floorPriceNanoTons`; нераспознанный ответ даёт пустой список (используются модели из листингов), `check` показывает результат | tgmrkts |

Поля подарка (по pydantic-моделям `amrkt`): `id`, `name`, `number`, `collectionName`, `collectionTitle`,
`modelName`, `modelRarityPerMille`, `backdropName`, `backdropRarityPerMille`, `symbolName`,
`symbolRarityPerMille`, `salePrice` (nanoTON), `isOnSale`, `isOnAuction`, `isMine`,
`backdropColorsCenterColor`, `backdropColorsEdgeColor`, `backdropColorsTextColor`,
`backdropColorsSymbolColor`, `floorPriceNanoTONsByCollection`, `floorPriceNanoTONsByBackdropModel`.
Отсутствующие поля бот не заменяет нулями: в интерфейсе они показываются как «Нет данных».

### Картинки подарков (мини-приложение)

По справочнику сообщества [Nxrix/Telegram-Gifts](https://github.com/Nxrix/Telegram-Gifts): обложка коллекции
`https://fragment.com/file/gifts/[giftname]/thumb.webp`, изображение подарка
`https://nft.fragment.com/gift/[giftname]-[id].webp`, где `giftname` — имя коллекции строчными буквами
(как в ссылке `t.me/nft/PlushPepe-1`, только строчными). Имя берётся из поля `name` подарка MRKT, а если
подарков коллекции бот ещё не видел — из названия коллекции без пробелов и знаков. Пара «модель + фон» —
`photo_url` записи Gift Wiki. Числового «процента монохромности» Gift Wiki не публикует: есть только уровень
`type` (`low` / `medium` / `high` / `combo`), его и показывает приложение.

### Что не подтверждено

* **WebSocket или потоковых обновлений нет ни в одном источнике.** Поэтому мониторинг работает
  через опрос `POST /feed` (резервный вариант: `POST /gifts/saling` с сортировкой по времени выставления)
  с ограничением частоты (`MRKT_REQUESTS_PER_SECOND`) и паузами на `429 Retry-After`.
* Лимиты частоты запросов MRKT не опубликованы. По умолчанию бот делает 2 запроса в секунду.
* Формат deep-link на конкретный листинг в API не задокументирован. Кнопка «Поделиться» в карточке
  подарка в Mini App MRKT даёт ссылку `https://t.me/mrkt/app?startapp=<32 шестнадцатеричных символа>` —
  это id подарка MRKT (тот, что передаётся в `gifts/buy`) без дефисов. По этому образцу (ссылку прислал
  пользователь из приложения MRKT) бот строит кнопку «Открыть в MRKT»; шаблон можно заменить в
  `MRKT_LISTING_URL_TEMPLATE` (плейсхолдеры `{gift_id}`, `{gift_id_hex}`, `{slug}`, `{number}`).
  Ссылка `https://t.me/nft/<slug>` строится, только если поле `name` имеет вид `Slug-123`.
* Идемпотентность `POST /gifts/buy` не задокументирована. Поэтому бот никогда не повторяет покупку
  автоматически после сетевой ошибки: сначала он проверяет состояние подарка (см. README, «Покупки»).

## 3. Определение «монохрома» в сообществе

Тематические каналы называют монохромом подарок, у которого цвет фона совпадает с цветом модели.
Бот не определяет монохромность сам: ни по названию, ни по цвету, ни по изображению. Он использует
только записи Gift Wiki, а цвета применяет лишь для сверки, что фон в записи и в листинге один и тот же.
